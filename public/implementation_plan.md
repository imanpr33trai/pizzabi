## 1. Executive Summary

### Purpose & Scope
This document upgrades the earlier V1 Custom Pizza Builder plan into a unified, implementation-ready UI/UX improvement specification for the **entire customer-facing PIZZORA / PIZZABI Android application** — spanning Authentication & Onboarding, Customer Navigation Shell, Menu & Discovery, Custom Pizza Builder, Cart & Re-Edit, Checkout & Scheduling, Razorpay / COD Payments, Live Order Tracking & Order History, Profile & Saved Addresses, Notifications Inbox & Preferences, and In-App Updates.

> **Naming Policy (Verified in Repo — Accepted Default for Phases 1–7):** The repository and project brief refer to **PIZZABI**, while `app/src/main/res/values/strings.xml`, `Theme.kt`, and package/brand assets use **PIZZORA** (`"Pizzora"`). **Decision #1 Policy:** `PIZZORA` is the **accepted default** for Phases 1–7 and **does not block Phase 1** unless the stakeholder explicitly directs a brand rename to `PIZZABI` before implementation begins (tracked in Section 14).

### Core Strategic Goals
1. **Eliminate Ordering Friction:** Remove double-scrim/trapped overlays, broken pricing sync between Cart and Checkout, missing order review before payment, and accidental destructive taps (single-tap Cart Clear, Address Delete, Sign Out).
2. **Deliver Commercial Food-Ordering Polish:** Restore appetite-led food photography across Menu, Custom Pizza Builder, and Cart; replace raw backend enum strings (`OUT_FOR_DELIVERY`, `COD_PENDING`, `ORDER_UPDATE`) and raw UTC timestamps with human-centered customer copy and localized IST formatting.
3. **Unify the Visual Design System:** Preserve the warm dark espresso (`#121110` / `#1D1A18`), Fraunces serif, warm parchment (`#F7F2EC`), coral terracotta (`#EF644F`), and mint basil (`#52B788`) identity while fixing systemic gaps: missing `titleSmall`/`bodySmall`/`labelSmall` typography definitions (currently silently falling back to Roboto), missing `errorContainer`/`onErrorContainer` theme tokens, and WCAG 2.2 AA contrast failures (`1.17:1` card/control borders in Dark mode and `3.19:1` amber text in Light mode).
4. **Stay Strictly Grounded in Real Backend Contracts:** Distinguish clearly between UI-only improvements, existing API integrations (e.g., notification deep-linking via existing `referenceId`, cart item photos via existing `CartItemEntity.imageUrl`, live payment countdown via existing `expiresAt`), true backend dependencies (Cheese/Sauce/Standard Toppings/Half-and-Half, saved favorites, order ratings), and future enhancements.

### Preserved Decisions From V1 Plan
- **Unimplemented Pizza Modifiers (Cheese, Sauces, Standard Toppings, Half-and-Half):** Build extensible `CustomizationSectionSlot` UI architecture now and explicitly flag backend/contract/Rust gaps rather than inventing client-only pricing rules.
- **Custom Pizza Builder Container:** Adaptive full-screen builder on phones + 2-pane split workspace on tablets (`>= 600dp × 480dp`) hosted at the `CustomerRoleShell` overlay layer (above top/bottom navigation), with a 92% bottom sheet preserved as an evaluated alternative.
- **Builder Pricing Presentation:** Sticky bottom dock featuring a collapsed configuration summary and an **expandable itemized price breakdown drawer** (Base Size + Crust + Extra Toppings × Qty + honest GST/delivery disclosure).
- **Cart Re-Edit Flow:** Included as a dedicated phase after core Custom Pizza Builder delivery so customers can edit existing customized cart items without delete-and-rebuild friction.

## 3. Problems and Opportunities

### Systemic Cross-App Weaknesses (Evidence-Based)
| Severity | Problem | Exact Code Evidence | Customer Impact |
|---|---|---|---|
| **Critical** | **Silent Roboto typography fallback** | `Type.kt` omits `titleSmall`, `bodySmall`, and `labelSmall` from `PizzoraTypography`. Used across `CartScreen`, `CheckoutScreen`, `OrdersScreen`, `CustomerProfileScreen`, `NotificationsScreen`, `CouponPickerSheet`, `UpdateScreens`. | Breaks brand typography cohesion on captions, badges, and section subheaders. |

### Cross-Journey Friction Fixes
- **Checkout Navigation Continuity:** Moving `CheckoutScreen` out of the Cart tab content body to a full-screen `CustomerRoleShell` overlay (matching `NotificationsScreen` and the new `PizzaBuilderScreen`) removes the distracting bottom navigation bar during payment commitment and keeps back navigation predictable (`Checkout -> Cart`).
- **Cart Badge & Price Continuity:** Every transition from Builder -> Cart -> Checkout -> Payment displays consistent `JetBrains Mono` tabular INR totals (`₹X.XX`), strictly adhering to the Authoritative Pricing Specification below.

### 4.3 Authoritative Pricing Consistency & Trust Specification *(Independently Audited Against `PricingEngine.kt`, `Money.kt`, `pizzora-core/src/pricing.rs`, `pizzora-api`, `PricingService.kt`, `CheckoutService.kt`, `PaymentService.kt`, `DomainBridge.kt`, and `RazorpayCheckoutLauncher.kt`)*

Every customer-visible monetary display across Menu, Builder, Cart, Checkout, Payment, and Order Detail MUST conform to this single pricing specification. Each rule is explicitly tagged with its Round 5 verification classification.

#### Authoritative 4-Level End-to-End Pricing Lifecycle
```
[LEVEL 1: LOCAL ESTIMATE]                   [LEVEL 2: SERVER QUOTE]
Menu / Builder / Unquoted Cart / Offline    Cart (Quoted) & Checkout (Auto-Synced)
• DomainBridge.calculateLineTotalPaise      • POST /v1/pricing/quote -> PriceBreakdownDto
• Uses cached catalog absolute variant      • Server IGNORES client_unit_price_paise &
  price + crust + toppings × qty (1..25)      re-prices from live DB catalog
• NEVER labeled "Total Payable"             • Authoritative pre-order total ("Total Payable")
• Shows honest "+ GST & delivery in Cart"   • Stale/failed quote MUST dim & lock Place Order
                    │                                           │
                    └──────────────────►────────────────────────┘
                                                                │ POST /v1/orders
                                                                ▼
[LEVEL 4: ACTUAL PAYMENT AMOUNT]            [LEVEL 3: CONFIRMED ORDER AMOUNT]
RazorpayPaymentSheet -> Razorpay SDK        OrderDetailScreen & Order Receipt
• payments.amount_paise &                   • OrderDetailDto snapshot persisted at checkout:
  payment_attempts.amount_paise               subtotal, discount, delivery_fee, tax, cgst,
  (written from breakdown.total_paise)        sgst, total_paise, gst_bps_snapshot
• Bound to latestAttempt?.amountPaise       • Immutable even if menu/coupon/zone later change
  ?: order.totalPaise (retry.enabled=false) • Price-drift notice if != last Level 2 quote
```

#### Canonical Pricing Formula & Verification Reference Table (All 13 Lifecycle Steps)
| # | Lifecycle Component | Exact Verified Formula / Backend Contract | Classification | UI Label & Display Rule |
|---|---|---|---|---|
| **1** | **Base Product Price** | Catalog product has no standalone checkout price; Menu displays `minPricePaise` (lowest active variant price). | *Verified in source code* (`CatalogDto.kt`, `CustomerMenuScreen.kt`) | Menu: `"From ₹X.XX"` (`PizzoraMonoTitle`). |
| **2** | **Size / Variant Pricing** | **Absolute prices** (`ProductVariantDto.pricePaise` / `CatalogVariantRef.price_paise`) — **NOT incremental deltas**. | *Verified in source code* (`pricing.rs`, `PricingService.kt`) | Builder Size cards: full `"₹X.XX"` (`PizzoraMonoBody`). |
| **3** | **Crust Pricing** | `crust.extraPricePaise` (`Long >= 0L`) added directly to variant price. | *Verified in source code* (`pricing.rs`, `PricingService.kt`) | `0L`: `"Included"` (`secondary`); `> 0L`: `"+₹X.XX"`. |
| **4** | **Extra Toppings Pricing** | `sum(selectedToppings.extraPricePaise)` (overflow checked via `checked_add`/`Math.addExact`). Unit price = `variant + crust + sum(toppings)`. | *Verified in source code* (`cart_validation.rs`, `PricingService.kt`) | Row: `"+₹X.XX"`; Builder breakdown aggregates `"+₹Z.XX"` & shows Unit Price when `qty > 1`. |
| **5** | **Quantity Multiplication & Limits** | `DomainBridge.calculateLineTotalPaise(unitPricePaise, quantity)` (`Math.multiplyExact` / `checked_mul`). `quantity in 1..25` (`MAX_ITEM_QUANTITY = 25`), `MAX_CART_LINE_ITEMS = 50`. | *Verified in source code & tests* (`PricingEngine.kt`, `pricing.rs`, `PricingEngineTest.kt`) | `× N` tabular mono; `+` disabled at `25` (`"Max 25 per item"`). |
| **6** | **Cart Subtotal (`subtotalPaise`)** | Exact sum of all line totals (`checked_add` / `Math.addExact`), pre-discount & pre-tax. | *Verified in source code & tests* (`PricingEngine.kt`, `pricing.rs`) | Builder: `"Item Total"`; Cart/Checkout: `"Item Subtotal"`. |
| **7** | **Coupon Eligibility & Discount (`discountPaise`)** | Evaluated against **pre-discount `subtotalPaise`**. Inactive or `subtotalPaise < coupon.minOrderPaise` -> `0L` (API throws `COUPON_MIN_ORDER_NOT_MET` / `COUPON_INACTIVE`). `PERCENT_BPS`: exact integer `HALF_UP` `(subtotal * bps + 5_000) / 10_000`; `FLAT_PAISE`: flat paise. Capped at `maxDiscountPaise` (if non-null) and `subtotalPaise`. | *Verified in source code & tests* (`PricingEngine.kt` L31–48, `pricing.rs`, `CouponService.kt` L595) | Basil green `"-₹X.XX"` with code chip; invalidation shows server reason in `warningContainer`. |
| **8** | **Taxable Amount & GST (`taxPaise`)** | Applied **strictly to discounted taxable items — NEVER to `deliveryFeePaise`**. Mixed taxable/non-taxable lines allocate discount proportionally via integer `HALF_UP`: `(discount * taxableSubtotal + subtotal / 2) / subtotal`. `taxPaise = Money.bpsOf(taxableAmountPaise, gstBps)` (`(amount * bps + 5_000) / 10_000`; `gstBps in 0..2800`, default `500` = 5% if settings row absent). #### Canonical Checkout Quote-Request Signature, Freshness & Race-Protection Contract *(Audited Against `PricingDto.kt` L78–84, `CheckoutQuoteViewModel.kt` L105–324, `CheckoutViewModel.kt` L367–378, `PricingService.kt` L64–108, and `services/pricing.rs` L63–129)*

1. **Source-Verified `PricingQuoteRequest` Inputs (No Invented Fields):**
   - `items: List<CartItemInputDto>` — each available line carries `(id, productId, variantId, crustId, toppingIds: List<String>, quantity: Int)` plus `clientUnitPricePaise: Long?` (**ignored by both backends**). Both backends deduplicate & sort `toppingIds`; **no per-topping quantities exist** in DTOs, Room, or either backend. *(Verified Bug in Existing `CheckoutQuoteViewModel.kt` L320–324: `List<CartItemWithToppings>.toSignature()` currently omits `productId` and covers only cart lines — Phase 5 MUST fix this.)*
   - `fulfillmentType: FulfillmentType` (`DELIVERY` | `PICKUP`).
   - `pincode: String?` & `addressId: String?` — when `DELIVERY`, both Kotlin (`PricingService.kt` L64, L91) and Rust (`services/pricing.rs` L63–90) accept `pincode` or `addressId` (resolving owned address pincode if `pincode` is blank; `pincode` takes precedence if both are sent). Current `CheckoutQuoteViewModel.kt` (L241–256) passes `pincode` only (`addressId = null`). When `PICKUP`, both backends ignore `pincode`/`addressId` and set `deliveryFeePaise = 0L`.
   - `couponCode: String?` — trimmed/uppercased, or `null` if blank.
   - **Explicitly Excluded (Not Read by `/v1/pricing/quote`):** `paymentMethod`, `scheduleType`, `selectedSlotId`, and `clientUnitPricePaise` MUST NOT invalidate or re-trigger pricing quotes.
2. **Canonical `QuoteRequestSignature` Definition:**
   ```text
   QuoteRequestSignature(
     itemsConfig          = availableItems.map { (id, productId, variantId, crustId, toppingIds.distinct().sorted(), quantity) },
     hasUnavailableItems  = cartItems.any { !it.item.isAvailable },
     fulfillmentType      = fulfillmentType,                                    // DELIVERY | PICKUP
     deliveryContext      = if (fulfillmentType == PICKUP) "PICKUP"
                            else "${effectivePincode.orEmpty()}|${effectiveAddressIdIfSent.orEmpty()}",
     normalizedCouponCode = couponCode?.trim()?.uppercase()?.takeIf { it.isNotEmpty() }
   )
   ```
   - *Same-Pincode, Different Saved Address Rule:* While `CheckoutQuoteViewModel` quotes by `pincode` (`addressId = null`), switching between two saved addresses sharing the same 6-digit pincode (e.g., Home `560001` -> Office `560001`) yields an **identical pricing-equivalence `QuoteRequestSignature`** — no redundant `POST /v1/pricing/quote` call is required, while `CheckoutViewModel.selectAddress()` updates `selectedAddressId` (which refreshes the `CheckoutRequest` idempotency signature at `CheckoutViewModel.kt` L367–378) and binds the order delivery address. If a future update sends `addressId` in `PricingQuoteRequest`, `effectiveAddressIdIfSent` changes the signature so the server re-verifies address ownership.
3. **Strict Separation of 4 Distinct Concepts:**
   - **Request Deduplication:** Do NOT fire a duplicate `POST /v1/pricing/quote` when `currentQuoteSignature` already matches an active in-flight request (`inFlightSignature == currentQuoteSignature`) or an already-fresh quote (`quotedSignature == currentQuoteSignature && quote != null && quoteError == null`).
   - **Quote Freshness:** `isQuoteFresh = (quote != null && quotedSignature == currentQuoteSignature && !isLoadingQuote && quoteError == null && !hasUnavailableItems)`. Any mutation to cart items/modifiers/quantities, fulfillment type, delivery pincode (or `addressId` if sent), or coupon code immediately makes `quotedSignature != currentQuoteSignature` -> `isQuoteStale = true`, dimming displayed totals (`0.6f`) with `"Updating total..."` and disabling `Place Order` until a fresh matching quote returns.
   - **Response Ordering & Race Protection *(Fixing Existing Bugs at `CheckoutQuoteViewModel.kt` L116, L279–291)*:** Maintain a monotonic `quoteRequestGeneration: Long` counter incremented before every `POST /v1/pricing/quote` dispatch **and** before the coupon-error fallback retry (L279–291), paired with explicit `quoteJob?.cancel()` and `zoneCheckJob?.cancel()` (fixing the uncanceled `applyPincodeCheck()` coroutine at L116). Every `.onSuccess`/`.onFailure` handler MUST guard `if (gen != quoteRequestGeneration || !isActive) return@launch` so cancelled, retried, or late responses can **never** overwrite newer state or clear a newer request's `isLoadingQuote`.
   - **Submission Eligibility (`Place Order` Acceptance Rule):** `Place Order` is enabled **ONLY** when ALL hold simultaneously:
     1. `isQuoteFresh == true` (non-null `quote` matching `currentQuoteSignature`, zero `quoteError`, `!isLoadingQuote`)
     2. `quote.isAcceptingOrders == true`
     3. `cartItems.isNotEmpty() && cartItems.all { it.item.isAvailable }`
     4. If `DELIVERY`: `selectedAddressId != null`, `quote.deliveryZone != null`, `quote.deliveryZone.pincode == selectedAddress.pincode`, and authoritative `quote.breakdown.subtotalPaise >= quote.deliveryZone.minOrderPaise`
     5. If `SCHEDULED`: a bookable `selectedSlotId != null` is chosen
     6. `!isPlacingOrder && !isCheckingZone && !isCheckingAddressZone`

#### Quote Invalidation & Race-Safety Scenarios (8 Verified Cases)
| # | Trigger Scenario | Effect on `QuoteRequestSignature` | Required State & UI Behavior |
|---|---|---|---|
| **1** | **Cart quantity change** | `itemsConfig` changes | Immediately `isQuoteStale = true`; cancel prior `quoteJob`; increment `quoteRequestGeneration`; refresh quote; re-evaluate coupon & `minOrderPaise`. |
| **2** | **Cart item edit or removal** | `itemsConfig` (or `hasUnavailableItems`) changes | Immediately `isQuoteStale = true`; if cart becomes empty, clear `quote = null` & `quotedSignature = null`; else cancel prior job and re-quote. |
| **3** | **Coupon apply / remove / invalidation** | `normalizedCouponCode` changes | Cancel prior job, increment generation, re-quote. On coupon rejection (`COUPON_*`), show `couponError` in `warningContainer`, increment generation before fallback un-couponed quote (`L279–291`), and update `quotedSignature` to the un-couponed signature. |
| **4** | **Delivery <-> Pickup switch** | `fulfillmentType` & `deliveryContext` change | Cancel `zoneCheckJob` & `quoteJob`, increment generation, immediately mark stale, re-quote (`PICKUP` sets `deliveryFeePaise = 0L` and clears delivery zone errors). |
| **5** | **Address switch (different pincode)** | `deliveryContext` changes | Cancel prior `zoneCheckJob` & `quoteJob`, increment generation, mark stale (`0.6f` dim), run 1 zone check + 1 quote sync for the new pincode, re-evaluate `minOrderPaise`. |
| **6** | **Address switch (same pincode)** | Unchanged *(when quoting by `pincode`)* | Reuse fresh quote without redundant `/v1/pricing/quote` call; `CheckoutViewModel.selectAddress()` updates `selectedAddressId` & order idempotency signature. *(If `addressId` is passed in quote request, signature changes and re-quotes.)* |
| **7** | **Network failure / timeout** | Unchanged (freshness broken by `quoteError`) | Do NOT clear Level 1 local subtotal; set `quoteError`, set `quotedSignature = null` (or `isQuoteStale = true`), show `errorContainer` + `Retry`, and **disable `Place Order`**. |
| **8** | **Out-of-order / cancelled late response** | Late response `gen < quoteRequestGeneration` | Drop late response completely (`if (gen != quoteRequestGeneration || !isActive) return@launch`); never publish stale `quote`, never overwrite newer `quoteError`, never clear active `isLoadingQuote`. |

#### Failure, Drift & Payment-Consistency Governance Rules
- **Silent Server Re-Pricing / Price-Drift Notice *(Verified Behavior -> Proposed UI Safeguard)*:** Both Kotlin and Rust backends intentionally **ignore `client_unit_price_paise`** and re-price every item from live DB catalog prices (`pg18_http_contracts.rs` L626, `Phase8PricingAndCouponsTest.kt` L415) without returning a `PRICE_CHANGED` error. Therefore, Android MUST compare `quote.breakdown.subtotalPaise != localCartSubtotalPaise` (in Cart/Checkout) and `createdOrder.totalPaise != lastQuotedTotalPaise` (after `POST /v1/orders`) and surface an explicit `warningContainer` / snackbar notice (*"Menu prices updated — your total has been refreshed to ₹X.XX"*) whenever a drift occurs.
- **Fixing Existing Stale-Quote Bug (`CheckoutQuoteViewModel.kt` L292–307):** Currently, when `requestQuote()` fails with `ZONE_UNSERVICEABLE`, `DELIVERY_MIN_ORDER_NOT_MET`, or a network error, `CheckoutQuoteViewModel` sets `quoteError` **without clearing `quote`**. Phase 5 MUST clear `quote = null` & `quotedSignature = null` on `ZONE_UNSERVICEABLE` / `DELIVERY_MIN_ORDER_NOT_MET` / invalid pincode, mark `isQuoteStale = true` on any signature mismatch or network failure, and lock `Place Order` until a fresh matching quote succeeds.
- **Payment Retries & Zero-Total Guard:** Payment retries strictly charge the locked Level 4 attempt amount (`latestAttempt?.amountPaise ?: order.totalPaise`). If a 100% flat coupon drives `totalPaise == 0L`, surface the server's `ZERO_ORDER_TOTAL` message clearly rather than enabling a `₹0.00` Razorpay launch.

## 7. Interaction Specifications

### 7.1 Motion & Transitions
- **Duration Tokens:** Fast micro-feedback `150ms` (selection borders, checkmarks, quantity bump), standard container reveal `220ms–260ms` (price breakdown drawer expand/collapse, Checkout items summary), screen transitions `280ms` (`fadeIn + slideInVertically(initialOffsetY = { it / 10 })` for full-screen Builder & Checkout overlays).
- **Reduced Motion Compliance:** Query `Settings.Global.ANIMATOR_DURATION_SCALE == 0f` (via helper `LocalReducedMotion`); when enabled, replace slide/spring/shimmer animations with instant crossfade or static tonal placeholders.

### 7.2 Micro-Interactions & State Feedback
- **Single Primary CTA Rule:** Every screen/viewport exposes at most **one** filled coral `Button` at a time (`Customize`/`Add to Cart`/`Proceed to Checkout`/`Place Order`/`Pay Securely`). Utility actions (`Check Pincode`, `Sync`, `Apply Coupon`, `Edit`) use `OutlinedButton`, `FilledTonalButton`, or `TextButton`.
- **Optimistic & Guarded Mutations:**
  - *Builder Add/Update:* Immediate button disable + subtle spinner until Room write resolves -> close overlay -> confirmation snackbar.
  - *Cart Qty Change:* Instant Room update with haptic light tick; `1 -> 0` or trash triggers immediate removal + 4s `"Undo"` snackbar.
  - *Cart Clear / Address Delete / Sign Out:* Explicit confirmation modal before mutating state.
  - *Checkout Place Order:* Uses existing idempotency key; disables button and shows `"Placing your order..."` spinner until navigation to Order Detail / Razorpay Payment Sheet completes.
- **Error, Loading & Offline Parity:**
  - *Initial Load:* Card-silhouette shimmer skeletons on Menu, Orders, and Profile (not bare `LinearProgressIndicator` on blank canvas).
  - *Inline Refresh:* Subtle top `LinearProgressIndicator` or `PullToRefreshBox` spinner preserving visible content.
  - *Offline Mode:* Persistent non-blocking warm amber `PizzoraStatusBanner` explaining cached data and sync behavior; disable network-only mutations (Checkout, Payment, Address Save) with clear messaging while keeping local Menu browsing & Cart editing functional.

### 7.3 Sticky Bottom Dock & Soft Keyboard (IME) Policy *(Added in Round 2)*
- **Builder & Checkout (Minimal/Modal Text Input):** Sticky `PizzoraStickyActionDock` stays anchored above navigation bars via `navigationBarsPadding()`. Modal forms (`AddAddressDialog`, `EditProfileDialog`, `CancelOrderDialog`) apply `imePadding()` so inputs and Save/Confirm actions stay visible above the soft keyboard.
- **Cart (Inline Pincode & Coupon Inputs):** Because `delivery_pincode_input` and `coupon_code_input` sit inline inside `cart_lazy_column`, pinning the sticky checkout dock *above* the soft keyboard collapses the viewport to `<150dp` on phones. **Rule:** Apply `imePadding()` to `cart_lazy_column` and automatically collapse/hide `PizzoraStickyActionDock` while `WindowInsets.isImeVisible` is true (`AnimatedVisibility` fade/slide out), restoring it instantly when the keyboard dismisses.

### 7.4 Live WebSocket & Payment Countdown Visual Grammar *(Added in Round 2)*
- **Order Tracking Freshness States (Zero Technical Telemetry):**
  1. *Live Connected:* `8dp` basil-green (`secondary`) dot + `"Live updates active"` (`bodySmall`, `onSurfaceVariant`).
  2. *Reconnecting / Polling Fallback:* Warm amber (`warningContainer` / `onWarningContainer`) compact inline notice + `"Reconnecting — checking latest status"`.
  3. *Offline / Disconnected:* Neutral `surfaceVariant` notice + `"Offline — pull down to refresh"` with explicit `"Refresh"` `TextButton`.
- **Payment Expiry Countdown (`expiresAt`):**
  - `> 3 min remaining`: Neutral `surfaceVariant` bar with tabular mono timer (`"Complete payment within 12:45"`).
  - `<= 3 min remaining`: Escalates to `warningContainer` / `onWarningContainer` (`"Expires in 02:18 — complete payment now"`).
  - `00:00 reached`: Stops ticker, disables `"Pay Securely"` button, shows `errorContainer` banner (`"Payment window expired"`), and triggers `ordersViewModel.refreshOrderDetail()` so server expiry state reconciles immediately.
  - *TalkBack Protection:* Never mark the 1-second timer text itself as a live region (would interrupt TalkBack continuously); announce expiry milestones only at `5m`, `2m`, `1m`, and `Expired`.

### 7.5 Dynamic Pricing & Coupon Transitions *(Refined in Rounds 2 & 6)*
- Any mutation changing `QuoteRequestSignature` (cart quantity/edit/remove, Fulfillment `Delivery` <-> `Pickup`, coupon apply/remove/invalidate, or switching to a saved address with a different pincode) immediately marks `isQuoteStale = true`, dims the breakdown (`0.6f` alpha) with `"Updating total..."`, cancels superseded `zoneCheckJob`/`quoteJob` coroutines, and dispatches under a fresh `quoteRequestGeneration`.
- Once the matching fresh Level 2 quote returns, animate the sticky dock Total via `AnimatedContent` (`150ms` vertical fade, instant when `LocalReducedMotion` is true) and trigger a polite accessibility announcement (`"Total updated to ₹468.00"`). Superseded/late responses (`gen < quoteRequestGeneration`) are silently discarded and never flicker totals.
- If lowering item quantity in Cart drops subtotal below an applied coupon's `minOrderPaise`, surface the server's inline invalidation explanation inside the coupon card (`warningContainer`) rather than silently dropping the discount without context, and increment `quoteRequestGeneration` before dispatching the fallback un-couponed quote.

### 10.4 Unverifiable / External Assumptions & Independent Design Critique *(Added in Round 4)*
- **Assumptions That Cannot Be Verified Without Live Device / External SDK Execution:**
  1. *Razorpay External Checkout Chrome:* Razorpay SDK `1.6.41` launches an external Activity/WebView whose internal UI cannot be fully themed to PIZZORA espresso dark (only brand accent hex and PIZZORA's pre-launch `RazorpayPaymentSheet` modal are under app control).
  2. *Live TalkBack Focus Traversal & Motion Feel:* Collapsing `PizzaBuilderScreen` header traversal order, `ModalBottomSheet` focus return, shimmer frame pacing, and haptic feedback amplitude can only be verified on physical Android devices / emulators during Phase 3–7 QA.
  3. *Foldable Hinge Postures & Extreme OEM Multi-Window:* Without `androidx.window:window`, hinge-spanning behavior on book/tabletop foldables is unverified and unsupported beyond window-size breakpoints.
  4. *Real-World WebSocket Reconnection Jitter:* Cellular-to-Wi-Fi handoff latency and carrier socket drops during live tracking require staging/device validation beyond Robolectric mock sockets.
- **Independent Design Critique (Genuine Remaining Weaknesses Preserved Transparently):**
  1. *Shell Overlay Flags vs. Typed Nav Routes:* Hosting Builder, Checkout, and Notifications via boolean/nullable shell state preserves existing Robolectric harness stability, but is less composable for future OS deep-links than migrating to typed Navigation Compose destinations.
  2. *Order History Scanability Without Item Previews:* Because `OrderSummaryDto` carries `itemCount` only (no pizza names), repeat customers scanning multiple past orders still rely on date + total + item count until the optional Phase 8 backend field lands.
  3. *No Cold-Restart Offline Order Tracking:* Verified in `PizzoraDatabase.kt` — without an `order_tracking` Room table, killing the app while offline clears visible order status until connectivity returns.
  4. *Dual Brand Naming (`PIZZORA` vs `PIZZABI`):* `PIZZORA` is the accepted default for Phases 1–7 (unblocking Phase 1); any future rename to `PIZZABI` requires an explicit stakeholder override (Section 14).
